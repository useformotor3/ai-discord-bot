# 검증 운영 프로토콜 — 빠르고 정확한 CRA/서보 드라이브 조사

- 버전: 1.0
- 기준일: 2026-11-12
- 상태: ACTIVE
- 목적: 조사량이 아니라 검증된 설계·시험 결과를 빠르게 만들고, 근거 없는 확정을 방지한다.
- 적용: CRA 법령, EU 공식 가이드, ST/TI 부품 기술자료, 표준·시험, 제품 적용성, 아카이브 정정

## 1. 작업의 완료 정의

작업은 문서 작성이나 검색 결과 수집만으로 완료되지 않는다. 다음 산출물이 연결되어야 완료로 본다.

1. Atomic claim: 한 문장에 하나의 검증 가능한 주장
2. Primary evidence: 공식 원문 URL, 문서명/번호, 버전/개정일, 정확한 조항·절·페이지
3. Evidence excerpt: 직접 인용은 원문 그대로 최소 범위로 기록. 번역·요약은 인용부호 없이 별도 필드에 둔다.
4. Independent check: 최초 확인과 구분되는 재검증 절차 및 결과
5. Applicability: 해당 법령/기능이 서보 드라이브 제품 경계와 정확한 부품번호에 어떻게 적용되는지
6. Engineering action: HW/FW/통신/제조/운영 요구로 번역
7. Verification: 시험 방법, 합격 기준, 객관적 증거물
8. Residual uncertainty: 미확인 조건, 충돌, 담당자 결정 사항

위 항목 중 하나라도 빠지면 관련 claim은 VERIFIED가 될 수 없다.

## 2. 증거 등급과 검증 상태

### 2.1 증거 등급
- E1 — 법령·EU 관보·공식 표준 원문·정확한 부품 데이터시트/Reference Manual/Errata/보안 공지
- E2 — European Commission/ENISA/표준기관/제조사 공식 애플리케이션 노트·공식 기술 가이드
- E3 — 학술 논문·공인 시험기관·신뢰 가능한 기술기관
- E4 — 산업 기사·블로그·포럼·검색 스니펫
- E5 — AI 생성 요약, 기존 archive 주장, 출처 없는 문장

핵심 법적/부품 기능 주장은 E1을 우선한다. E2는 설명·해석 보조다. E3/E4는 보조 맥락이며 단독으로 법령 의무나 부품 기능을 확정하지 않는다. E5는 검증 후보일 뿐 증거로 취급하지 않는다.

### 2.2 상태
- VERIFIED: 원문·버전·위치·문맥 확인 + 별도 재검증 완료 + 제품 적용성 판단 완료(적용성 없는 일반 법령 문구는 그 부분 제외)
- PARTIALLY_VERIFIED: 원문 또는 일부 조건만 확인
- UNVERIFIED: 원문/제품 조건/시험 증거가 미확인
- CONFLICT: 신뢰 가능한 출처끼리 내용이 충돌
- OUTDATED: 개정·대체·폐지 확인
- NOT_APPLICABLE: 제품 경계와 적용 조건을 검토한 뒤 비적용 이유를 기록
- REJECTED: 원문과 불일치하거나 근거 없는 주장으로 확인되어 사용 중단

링크가 열림, 검색 결과에 제목이 나옴, 다른 AI가 동의함만으로 VERIFIED로 올리지 않는다.

## 3. 반드시 분리할 4개 주장 유형

| 유형 | 예 | 검증 방식 |
|---|---|---|
| 법령 사실 | CRA Article 13(8)의 지원기간 | EUR-Lex 원문과 조항 문맥을 직접 확인 |
| 기술 사실 | 특정 STM32 부품의 RDP/TrustZone 지원 | 정확한 주문 코드의 datasheet, RM, errata, 보안 공지 확인 |
| 해석/적용 | 특정 드라이브가 Important Class I인지 | 제품 경계·핵심 기능·시장 제공 형태를 법령 기준에 대입하고 반대 근거도 확인 |
| 설계 권고 | secure boot, 키 보호, 디버그 포트 정책 | 위험평가·위협모델·구현 가능성·시험 증거로 정당화. 법령의 문자 그대로의 의무와 혼동 금지 |

## 4. 더블체크: 독립성을 확보하는 방법

**같은 AI에게 같은 문장을 다시 물어보는 것만으로 독립 검증이라고 부르지 않는다.**

### Pass A — 최초 조사
- 주장을 원자 단위로 나눈다.
- 검색 결과가 아니라 공식 원문을 연다.
- 문서 식별자, 버전, 발행/개정일, 정확한 위치를 기록한다.
- 주장과 직접 인용/요약/해석을 분리한다.

### Pass B — 별도 재검증
- Pass A의 결론만 보고 동의하지 말고 원문 위치를 다시 연다.
- 앞뒤 문단, 정의, 예외, 적용 범위를 다시 확인한다.
- 조항 번호/Annex/항/점, 숫자·기간·단위, 조건어(예: where technically feasible)를 체크리스트로 대조한다.
- 제조사 기능은 데이터시트 외에 해당 부품의 Reference Manual, Errata, 공식 보안 공지/애플리케이션 노트와 교차 대조한다.
- 두 번째 공식 출처가 원문을 반복할 뿐 독립 증거가 아니면 “보조 확인”으로만 기록한다.
- 법령 원문이 유일한 권위 출처인 문구는 원문 재확인과 조항 문맥 검사를 독립 절차로 기록하고, 근거가 2개라고 과장하지 않는다.

### Pass C — 반증 시도
- 해당 주장을 틀리게 만들 수 있는 예외, 정의, scope exclusion, 제품 경계, 개정 이력, errata를 검색한다.
- 반대 근거가 발견되면 CONFLICT 또는 PARTIALLY_VERIFIED로 낮춘다.
- 반증 검색을 수행하지 못하면 미수행으로 기록한다.

### Pass D — 엔지니어링 리뷰
- “법령이 요구한다”와 “권장 설계”를 구분한다.
- 실제 회로/펌웨어에서 구현 가능한지, 부품별 제약이 있는지 확인한다.
- 시험 방법, 합격 기준, 저장할 증거가 정의되지 않은 설계 요구는 완료로 표시하지 않는다.

## 5. 효율을 위한 위험 기반 우선순위

### P0 — 잘못되면 제품/법적 판단을 뒤집는 항목
- CRA scope와 product boundary
- Article 7 / Annex III / Class I·II
- Article 13 제조자 의무 및 지원기간
- Article 14 신고 대상/시한
- Annex I Part I/II 보안 요구
- 실제 MCU 주문 코드, 보안 기능, 부트/업데이트/키 저장
- 안전·보안 경계 및 업데이트 실패 복구

### P1 — 설계/검증에 직접 필요한 항목
- Secure Boot/SFU/SFI 흐름, 키 프로비저닝, 디버그 lifecycle
- 통신 인터페이스/서비스 포트/원격 접근
- SBOM, 취약점 처리, 패치 정책, 지원 종료
- 시험 커버리지와 객관적 증거

### P2 — 설명·비교·보완
- 범용 개념 설명, 비핵심 제조사 비교, 참고 사례

P0부터 끝내되, 하나의 항목을 무한 조사하지 않는다. 핵심 원문·반증·적용성에 답이 나왔으면 다음 설계 결정으로 이동한다. 자료량이 늘어도 설계 결정이 바뀌지 않는 조사는 중단한다.

## 6. 각 claim의 필수 레코드

| 필드 | 필수 내용 |
|---|---|
| claim_id | 고유 ID |
| claim_text | 검증 가능한 단일 주장 |
| claim_type | LAW / TECH / INTERPRETATION / RECOMMENDATION |
| source_id | 출처 레지스트리 ID |
| canonical_url | 공식 원문 URL |
| document_id/version | 법령 번호, 부품 번호, 문서 번호와 개정 |
| source_location | 조항/항/점/페이지/절 |
| source_excerpt | 짧은 원문 발췌, 없으면 공란 |
| interpretation_ko | 한국어 해석/번역 |
| pass_a_result | 최초 확인 |
| pass_b_result | 별도 재검증 |
| pass_c_countercheck | 반증 검색 결과 |
| applicability | 제품/부품 조건 및 근거 |
| engineering_action | HW/FW/QA 조치 |
| test_and_acceptance | 시험 및 합격 기준 |
| evidence_artifact | 로그, 시험성적, 설정, 빌드 해시 등 |
| status | 위 상태 중 하나 |
| open_questions | 미해결 조건 |

## 7. 직접 인용 규칙
- 원문을 직접 열어 확인한 문장만 따옴표로 쓴다.
- 번역은 “한국어 번역”으로, 의미 설명은 “요약/해석”으로 표기한다.
- 중간 생략은 생략 표시를 하고, 문맥을 바꾸는 부분 생략은 금지한다.
- 서로 다른 조항을 한 문장으로 합쳐 직접 인용하지 않는다.
- 원문과 어긋난 문장은 REJECTED로 표시하고 정정본에서 제거한다.
- 페이지/조항/Annex 위치가 틀리면 문구가 유사해도 VERIFIED가 아니다.

## 8. 제품/MCU 적용성 게이트
제품별 판단을 시작하기 전에 다음이 필요하다.
- 제품 SKU/모델과 EU 시장 제공 형태
- intended purpose와 reasonably foreseeable use
- 네트워크/물리적 연결, 직접/간접 연결
- 원격 데이터 처리 기능과 그 기능이 제품 기능에 필수인지
- 드라이브 본체/옵션 모듈/툴/클라우드의 제품 경계
- MCU 전체 주문 코드, 실리콘 리비전, 메모리 옵션
- Secure Boot/TrustZone/crypto/secure storage/debug lock/TRNG 등 해당 부품의 실제 지원 조건

부품군 소개 자료만으로 부품 기능을 확정하지 않는다. MCU 기능만으로 완제품 CRA 등급을 확정하지 않는다.

## 9. 빠른 산출물 경로
조사 결과는 아래 순서로 산출물에 연결한다.
1. 법령 요구사항 레지스터
2. 제품 경계/적용성 결정표
3. 요구사항-위협-설계대책 매핑
4. HW/FW 보안 블록과 인터페이스
5. 구현 선택지 및 부품별 제약
6. 시험 계획/합격 기준/증거 목록
7. 취약점·업데이트·지원기간 운영 프로세스
8. 통합 개발자 보고서와 용어집

조사 주제별로 독립 보고서를 계속 늘리지 말고, 원본 근거 레지스터에 먼저 기록한 뒤 위 산출물에 반영한다.

## 10. 중단/승격 기준
- 핵심 근거가 없으면 설계 결론을 확정하지 않고 입력 질문으로 전환한다.
- 제품 SKU나 MCU 부품번호가 없으면 제품별 적용성/부품 기능은 UNVERIFIED로 유지하되, 일반 설계 아키텍처와 필요한 확인 항목은 진행한다.
- 법령 해석이 충돌하면 공식 가이드/관할기관 자료를 추가 확인하고, 해결되지 않으면 CONFLICT로 남긴다.
- 표본 감사는 표본 수, 선정 방식, 원본 해시, 검토 범위를 명시한다. 표본 결과를 전수 오류율로 표현하지 않는다.
- 모든 변경은 작은 단위로 커밋하고, 원본 archive는 보존한다.

## 11. 세션 종료 전 품질 게이트
- 필수 GitHub 문서를 다시 읽고 변경 상태를 대조한다.
- 신규 핵심 주장에 source URL/version/location이 있는지 검사한다.
- VERIFIED 상태에 Pass A/B와 반증 검토 기록이 있는지 확인한다.
- 테스트 결과와 workflow 상태를 실제 실행 결과로 확인한다.
- 미확인·실패·다음 작업을 기록한다.
- main.py/Gemini prompt/운영 흐름 변경은 사용자 승인 없이는 수행하지 않는다.

## 12. 다음 즉시 실행 우선순위
1. 이 프로토콜을 적용해 34개 표본 정정본을 별도 작성하고 원본과 혼동되지 않게 한다.
2. 나머지 archive는 P0 위험 후보부터 batch 처리한다. 단순 키워드 매칭을 오류 확정으로 사용하지 않는다.
3. 법령 baseline을 설계 요구사항/시험/증거 매트릭스로 변환한다.
4. 제품 경계 입력과 정확한 ST MCU 주문 코드가 확보되는 즉시 제품별 판단으로 전환한다.
5. ST/TI 문서 버전 불일치 및 미확인 링크를 해결하되, 실제 부품이 확인되지 않은 비교는 참고 사례로만 둔다.
