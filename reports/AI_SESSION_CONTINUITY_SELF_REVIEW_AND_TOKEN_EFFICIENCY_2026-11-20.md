# AI 세션 연속성·자기검토·토큰 효율 운영 기준

- 작성일: 2026-11-20 (KST)
- 적용 범위: CRA 전체 프로젝트의 조사·분석·코드·보고서·세션 운영
- 상태: 운영 기준 초안. `AI_RULEBOOK.md`의 보충 규칙이며, 이 문서가 대화 기억보다 우선하는 지속 기록이다.
- 목적: 모델 자체가 가중치를 바꾸거나 자율적으로 재학습하지 못한다는 한계를 인정하고, GitHub의 외부화된 기록·검증·피드백 루프로 재귀 개선과 유사한 운영을 구현한다.

## 1. 정직한 한계와 개선 루프

AI는 대화 사이에 스스로 코드를 수정하거나 가중치를 학습하는 지속적 자율 에이전트가 아니다. 따라서 "스스로 학습했다", "항상 기억한다", "자동으로 개선됐다"고 주장하지 않는다. 대신 매 작업에서 다음의 명시적 루프를 반복한다.

1. **기준 확인**: 최신 main, 활성 작업 브랜치, PR/CI, 상황판, 행동강령, 계획, 최근 로그와 원본 증거를 읽는다.
2. **작업 수행**: 범위가 승인된 최소 단위로 조사·수정한다.
3. **독립 검증**: 작성자 관점의 자체 점검과 별도 기준/원문/테스트를 이용한 반대 검토를 분리한다.
4. **실패 분석**: 오류·누락·오래된 정보·잘못된 주장·도구 한계를 사실과 추정으로 나누어 기록한다.
5. **규칙 개선**: 재발 방지 규칙, 자동 검사, 테스트 또는 체크리스트로 전환한다.
6. **영속화**: 변경·근거·검증·잔여 위험·다음 작업을 GitHub에 기록하고 read-back한다.
7. **다음 세션 재현**: 새 세션은 이 문서와 최신 상황판을 기준으로 시작한다.

개선 루프가 실제로 작동했다고 말하려면 GitHub 변경 또는 검증 가능한 작업 결과가 있어야 한다. 계획만 세운 것은 완료가 아니다.

## 2. 오류·잘못·개선점 기록 규칙

각 중대한 오류는 다음 필드를 갖춘다(해당 없는 항목은 N/A).

- ID / 발견일 / 관련 보고서·파일·claim ID
- 오류 유형: 법령·표준 상태·인용·제품 적용성·시점·코드·도구·기록 정합성
- 기존 주장 또는 행동과 실제 확인된 사실
- 영향 범위 및 위험도(P0–P3)
- 근본 원인: 오래된 스냅샷, 원문 미확인, 추론 과잉, 범위 혼동, 검증 미실행, 잘못된 도구 선택 등
- 교정 조치와 1차 출처/테스트 증거
- 재발 방지: 규칙·검사기·테스트·체크리스트 중 무엇을 추가했는지
- 검증 상태: 제안 / 구현 / 테스트 통과 / 독립 확인 / 미해결
- 잔여 한계와 재검토 조건

사소한 문장 수정은 세션 로그에 묶어 기록할 수 있으나, 법적 결론·안전·제품 분류·CI 오표시·데이터 손실 위험은 별도 항목으로 추적한다. 오류를 조용히 덮거나 과거의 잘못된 문서를 원본 기록 없이 덮어쓰지 않는다.

## 3. CRA 조사 품질 게이트

- 최신성이 중요한 법령·Commission/ENISA 안내·표준화·OJ citation·제조사 자료는 매 세션 최신 원문을 다시 확인한다. 과거 날짜가 붙은 상황판의 상태를 현재 상태로 복사하지 않는다.
- **서로 다른 상태를 합치지 않는다**: 표준 개발/ESO 제출/발행/조화표준 OJ 인용/Article 27 추정 적합성은 별개다. 법률 적용일과 ESO 작업기한도 별개다.
- 각 핵심 주장에 source ID, 공식 URL, 버전/날짜, 조회일, 정확한 조항·페이지·표/행 locator, 원문/취득 상태, hash(실제 취득한 경우), 해석, 반대 근거, 적용성, confidence를 연결한다.
- 웹 검색 결과 snippet 또는 검색 인덱스만으로 법적 결론을 내리지 않는다. 공식 원문을 열고 필요한 locator까지 확인한다.
- 독립 교차검증은 단순히 같은 내용을 반복 검색하는 것이 아니다. 가능하면 별도 공식 출처, 다른 원문 형식, 명시적 반례 또는 별도 검토 절차를 사용한다.
- 확인되지 않은 것은 Unknown/Not verified/Metadata only/Not run으로 남긴다. 자료 목록 확인을 문서 본문 검토로, CI 성공을 법적 정확성으로, 제품 기능 존재를 보안 통제 구현으로 확대 해석하지 않는다.
- 사용자 지적처럼 데이터 누락 가능성을 전제로 한다. "완전하다/100% 정확하다"는 표현을 쓰지 않고 조사 범위·검색 범위·누락 가능성을 표시한다.
- CRA 전체 규제·표준화 트랙을 지속 우선한다. LS메카피온/iX7NH는 제품 사례연구이며 CRA 핵심 조사보다 우선하지 않는다.

## 4. 토큰·도구 사용 효율

- 세션 시작 시 전체 저장소를 무차별 재독하지 않는다. 최신 main/PR 상태와 필수 관리 문서, 마지막 재개 지점, 그 지점 이후 변경분을 우선 읽는다.
- 이미 확인된 사실은 최신성/버전 변화가 의심되지 않는 한 재수집하지 않는다. 대신 원본 source ID·파일 경로·claim ID를 참조한다.
- 한 번의 조사 배치에서 서로 관련된 질문을 묶어 검색하되, 법적 상태가 다른 자료는 별도 claim으로 분리한다.
- 검색은 공식 1차 출처 우선, 좁은 질의부터 시작한다. 검색 결과가 부족하거나 상충할 때만 추가 질의를 확장한다.
- 긴 파일은 필요한 구간만 읽고, 파일 전체를 다시 출력하지 않는다. 요약은 근거 링크와 원본 locator를 보존한다.
- 코드·문서 작업은 최소 diff, 단일 목적 브랜치, 관련 테스트만 우선 실행한다. 테스트가 통과하면 필요한 전체 회귀 검증을 추가한다.
- 같은 내용을 README/상황판/계획/로그에 중복 서술하지 않는다. 각 문서는 역할을 지키고 상세 증거는 단일 보고서/대장에 둔다.
- 토큰 절약 때문에 검증을 생략하지 않는다. 핵심 근거·반대 근거·한계·검증 결과는 절대 생략 대상이 아니다.
- 작업 종료 시 장황한 대화 요약보다 재개 가능한 파일 경로, 브랜치, commit/PR, CI run, 다음 작업 1~3개를 기록한다.

## 5. GitHub 변경·복구·검증 게이트

1. 시작 전 main HEAD, 작업 브랜치 HEAD, PR 상태와 최근 CI를 확인한다.
2. main에서 짧은 작업 브랜치를 만들고 작업한다. 오래된 divergent branch를 최신 작업 브랜치인 것처럼 가정하지 않는다.
3. 변경 전 기준 SHA와 복구 ref를 기록한다. 기존 자료·로그·SIL 3 보존 자료를 임의 삭제하거나 대량 병합하지 않는다.
4. 문서 변경도 최소 diff 및 링크/표/수치 정합성을 검사한다.
5. 코드 변경은 source integrity → compile → targeted tests → full tests → exact-head CI 순으로 확인한다.
6. PR 병합 후 main read-back, merge SHA, post-merge safety ref 및 CI를 재확인한다. PR head CI와 main push CI를 혼동하지 않는다.
7. CI 성공은 그 workflow가 실제 수행한 검사만 증명한다. source canary, pytest, artifact upload 각각의 성공/skip/failure를 구분한다.
8. 모든 변경은 파일 경로·브랜치·커밋/PR·검증 증거와 함께 기록한다. read-back 전에는 저장 완료로 표현하지 않는다.
9. 저장소 main 보호 설정이 비활성화되어 있으면 명시적 거버넌스 위험으로 계속 표시하고, 수동 PR/CI/safety gate를 적용한다.

## 7. 현재 세션에서 반영해야 할 교훈 (2026-11-20)

- `PROJECT_STATUS.md`는 역사 기록이며 `PROJECT_STATUS_CURRENT.md`가 최신 재개 기준이다. 두 파일의 역할을 혼동하면 오래된 정보를 현재로 오인한다.
- LS메카피온/iX7NH 사례연구에 몰입하더라도 CRA 전체 법령·표준화·OJ·적합성 경로 트랙의 우선순위를 잃지 않는다.

## 8. 대화 단위 결과 검토와 개선점 선별 (2026-11-21)

각 대화 또는 실질적인 작업 배치가 끝날 때 다음을 점검한다. 단순한 '진행' 지시처럼 새 결과가 없는 턴은 기존 작업 상태를 이어가되, 중복 로그를 생성하지 않는다.

1. **요청 대비 결과**: 사용자가 요구한 목표·범위·우선순위와 실제 변경/산출물이 일치하는가?
2. **증거와 검증**: 무엇을 실제 실행·열람·테스트했는가? 계획, 성공한 도구 호출, 파일 저장, read-back, CI, 운영 효과를 서로 구분했는가?
3. **AI 행동 점검**: 사실을 추정으로 채웠는가, 오래된 상태를 재사용했는가, 필요한 도구/공식 출처를 놓쳤는가, 불필요한 검색·출력·파일 분리를 했는가?
4. **개선 선별**: 반복 가능하고 근거가 있으며 정확성·재현성·안전성·추적성·효율을 개선하는가? 아니면 이번 건에 한정된 수정인가?
5. **반영 수준**: 일회성 수정은 산출물에, 반복 절차는 운영 기준에, 기계적 회귀 오류는 테스트/검사기에, 구조적 문제는 별도 PR/이슈에 반영한다.
6. **효과 확인**: 개선 적용 후 테스트·read-back·다음 운영 실행에서 효과가 관찰되었는지 기록한다. 아직 확인 전이면 '적용됨/효과 미검증'으로 남긴다.

### 영구 반영 제외 기준
- 근거 없는 자기평가, 단순 선호, 일회성 우연, 이미 존재하는 규칙의 중복, 토큰을 아끼기 위해 필수 검증을 생략하는 제안은 영구 기준에 추가하지 않는다.
- 기록량 자체를 성과로 보지 않는다. 장기적으로 재사용할 가치가 있는 사실·결정·오류·재발 방지 규칙만 보존한다.

### 2026-11-21 관찰 사례
- 최신 ETSI Work Item 상태 V1.0.9와 실제 무료 공개 다운로드 V1.0.1을 혼동하지 않도록 버전·출처 유형별로 구분한다. V1.0.9 원문 미확보 상태를 명시한다.
- AI_RULEBOOK에 과거 버전 근거를 'latest publicly viewable draft'라고 쓴 문구가 새 V1.0.9 상태와 충돌할 수 있음을 발견했다. 역사적 증거로 격하하고 최신 원문 취득 게이트를 명문화한다.
- 행동강령의 뒤에 추가된 섹션 번호가 기존 1~59번과 중복되는 것을 확인했다. 새 섹션을 60번 이후로 정리해 문서 탐색성을 높인다.
- 이 개선은 문서 기준 정비 단계다. 다음 세션에서 재현성·누락 감소 효과가 확인되기 전까지 운영 효과가 입증됐다고 주장하지 않는다.


## 9. KST 날짜 경계 일일 개선 루프 (2026-11-21)

- 일일 기준일은 UTC가 아니라 Asia/Seoul 날짜로 관리한다. 세션 시작/재개 시 오늘 날짜와 마지막 실제 검토일을 비교하고, 날짜가 변경된 경우에만 일일 결과/행동 감사와 개선 후보 선별을 수행한다.
- 일일 루프의 기준 문서는 `AI_RECURSIVE_IMPROVEMENT_PROTOCOL.md`다. AI_RULEBOOK §72에는 실행 트리거와 필수 원칙만 두어 중복 규칙을 방지한다.
- 변경이 없으면 NO_CHANGE로 남기고, 매일 새 파일·커밋을 만들지 않는다. 개선이 있으면 증거·원인·영향·수정 수준·검증·잔여 위험을 기록한다.
- 상태는 PROPOSED / DOCUMENTED / TESTED / OPERATIONALLY_OBSERVED / REGRESSED / RETIRED로 구분한다. 장기 효과가 후속 작업에서 관찰되기 전에는 운영 효과가 입증됐다고 하지 않는다.
- 현재는 세션 시작/재개 시 수행하는 운영 절차다. 백그라운드 날짜 감시나 자동 커밋이 구현된 것처럼 말하지 않는다.
